Как читать пометки:
- **видно из кода** — механизм однозначен, спорить можно только о размере потери;
- **замер соседа** — число взято из профилей, которые в этой же сессии снял другой эксперт и положил рядом
  (`prof-load.txt`, `prof-pan.txt`, `prof-sheets.txt` в этой же папке: безголовый Chromium без видеокарты, экран телефона
  390×844, быстрый серверный процессор). Телефон слабее в 3–6 раз, поэтому эти числа — нижняя граница;
- **оценка** — моя прикидка по коду, без замера; чем проверить — сказано в пункте или в разделе 5.

Слова, которые встречаются часто:
- *перерисовка React* — React заново выполняет код экрана и сверяет результат со страницей; сама по себе картинку не меняет, но занимает процессор;
- *главный поток* — единственная «очередь», в которой браузер выполняет код страницы и отвечает на палец; пока он занят, экран не реагирует;
- *кадр* — одна картинка на экране; для плавности их нужно 60 в секунду, то есть на каждый не больше 16 мс;
- *стекло* — полупрозрачная панель с размытием того, что под ней (`backdrop-filter`);
- *холст* — прямоугольник, в котором код рисует сам (`canvas`); *WebGL* — рисование видеокартой.

## 1. Главное

Основа карты сделана грамотно: сдвиг и масштаб идут мимо React, мир и море уже на WebGL, тяжёлая геометрия считается
один раз, есть свой измеритель `?perf=1`. Тормозит не карта как таковая, а обвязка вокруг неё — и почти всё лечится
без изменения вида. Сильнее всего мешают:
1. обновление карты с сервера (раз в минуту, при возврате в приложение, по каждому событию) пересчитывает всё заново,
   включая поиск морских путей, — это и есть «подвисание на ровном месте»;
2. часы раз в секунду перерисовывают весь экран игрока вместе с картой, подписями и всеми датами открытого списка;
3. при открытии карты на главном потоке считаются обводка городов (0,8 с на быстром процессоре — замер соседа), догон
   живности, дно моря: на слабом телефоне это несколько секунд без отклика на палец;
4. под «стеклом» листов карта продолжает рисоваться 24–30 раз в секунду, и столько же раз заново размывается до 92 % экрана;
5. 10–12 холстов во весь экран и слой подписей в три экрана — порядка 100–150 МБ графической памяти (оценка): вероятная
   причина выгрузки приложения в фоне и «подгрузок».

Всего пунктов — 25 (24 находки и вывод по утечкам); первые шесть почти все малые по объёму и дают основную часть выигрыша.

## 3. Все находки

### A. Перерисовки React

#### A1. Часы раз в секунду перерисовывают весь экран игрока и карту

**Где:**
- `pages/TeamPage.tsx:242` и `:348` — состояние `now` и `setInterval(..., 1000)` на самом верху экрана;
- `now` на деле нужен только в трёх местах: `:911`, `:913`, `:919` (строки испытаний и их отсчёт);
- `pages/TeamPage.tsx:962–971` — карта получает новые функции при каждой перерисовке (`onLand`, `onMark`,
  `onFrontierTap`, `onSelectQuarry`, `onSelectWreck` написаны прямо в разметке; `tapMark` — `:527`, обычная функция);
- `pages/TeamMap.tsx:95` — `TeamMap` не обёрнут в `memo`; `:641` — список зависимостей `screenBody` содержит
  `onMarkTap` и `onFrontierTap`, которые каждый раз новые;
- `pages/TeamPage.tsx:627–687` — сортировки и выборки дел (с `localeCompare`) прямо в теле экрана, без `useMemo`;
- `pages/MapLayers.tsx:398` — `dirty.current = true` при каждой перерисовке слоя тумана;
- строки-ключи из всех гексов собираются при каждой перерисовке: `pages/TeamMap.tsx:101`, `pages/MapLayers.tsx:395`
  и `:556`, `pages/Fauna.tsx:2046`, `pages/Lakes.tsx:67`, `lib/keep.ts:15` (через `useCoast`, `useIslets`, `useSeabed`);
- то же внутри листов: `pages/CityPopup.tsx:108` и `pages/BattlePanel.tsx:55` — свои секундные часы на весь лист.

**Что не так:** таймер стоит в корне экрана. Раз в секунду React заново выполняет все 1350 строк `TeamPage`, затем
`TeamMap` и все девять слоёв карты. Запоминание (`useMemo`) у подписей карты не срабатывает, потому что в его
зависимостях стоят функции, которые создаются заново при каждой перерисовке, — поэтому все подписи, метки дел и значки
(сотни элементов SVG) раз в секунду собираются и сверяются заново. Открытый раздел («Дела», «Летопись», «Команды»)
перерисовывается целиком — со всеми датами (см. A3). Набор текста в полях «Найти дело» и «Подпись метки» делает то же
самое на каждую букву: их состояние тоже лежит в корне (`:220`, `:255`, `:263`).
В профиле соседа за 32 секунды перетаскивания карты без открытых листов форматирование дат заняло 342 мс, сортировка
дел `byTitle` — ещё 9 мс: это и есть ежесекундная перерисовка, видимая в цифрах.

**Как лучше:**
1. Часы — в листья. Маленький хук и маленький компонент, которые тикают сами:
   ```tsx
   function useNow(ms = 1000) {
     const [now, set] = useState(Date.now);
     useEffect(() => { const t = setInterval(() => set(Date.now()), ms); return () => clearInterval(t); }, [ms]);
     return now;
   }
   function BattleRow({ b, ...rest }) { const now = useNow(); /* строка испытания с отсчётом */ }
   ```
   Из `TeamPage` состояние `now` убрать совсем. В `CityPopup` и `WarSection` — так же: отсчёт паузы и срока в отдельном
   маленьком компоненте, а не на весь лист.
2. `export const TeamMap = memo(function TeamMap(...) { ... })`.
3. Обработчикам карты дать постоянную ссылку (приём «свежая функция через ref»):
   ```tsx
   function useEvent<T extends (...a: any[]) => any>(fn: T): T {
     const ref = useRef(fn); ref.current = fn;
     return useCallback(((...a) => ref.current(...a)) as T, []);
   }
   const onMarkTap = useEvent(tapMark);
   ```
   Тогда `screenBody` перестанет пересобираться без причины.
4. Списки дел (`ourTasks`, `freeTasks`, `freeGroups`, `knownCities`) — в `useMemo` от `map.tasks`; сравнение названий —
   одним заранее созданным `new Intl.Collator("ru")`.
5. Разделы меню (`FeedSection`, `MyServiceSection`, `StandingsList`) обернуть в `memo`, поля поиска и подписи метки
   вынести в свои компоненты с собственным состоянием.

**Что это даст:** между событиями экран и карта перестают перерисовываться вовсе. Оценка: минус 5–25 мс работы
каждую секунду на слабом телефоне при закрытых листах и минус 50–150 мс каждую секунду при открытой «Летописи» или
«Делах» (там сейчас раз в секунду форматируются все даты списка). Жесты перестают терять кадр раз в секунду.

**Объём работы:** малый (пункты 1–3 — час-два), средний вместе с 4–5.

**Риск:** низкий. Нужно проверить, что отсчёты в испытаниях и паузы в городе по-прежнему тикают; что нажатия на
метки и точки края тумана видят свежее состояние (для этого и нужен `useEvent`, а не простой `useCallback`).

#### A2. Любое обновление карты пересчитывает всё заново, включая поиск морских путей

**Где:**
- `pages/TeamPage.tsx:367` — `loadMap` кладёт в состояние свежий объект; `lib/api.ts:25` — `apiReady` всегда отдаёт
  заново разобранный ответ;
- когда зовётся: `pages/TeamPage.tsx:410–415` (каждые 60 секунд и при каждом возврате в окно), `:402` (события игры),
  `:441`, `:450`, `:460` и далее (после каждого своего действия);
- `pages/TeamPage.tsx:390–393` — разница карты от сервера: `structuredClone(cur)` и затем `applyPatch(..., true, false)`;
  четвёртый параметр `false` означает «сделай копию сам» — карта копируется дважды, и все её части становятся новыми объектами;
- что от этого пересчитывается в `pages/TeamMap.tsx`: `:172–177` (`positions`, зависит от всего `map`), `:227` (входы
  тумана), `:249–256` (`seaRoutes` — поиск пути по морю для каждой переправы), `:261–270` (хвосты чужих переправ — ещё
  поиск), `:315–319` (области нажатия), `:359–397` (сцена мира), `:461–641` (подписи);
- `packages/domain/src/seaRoute.ts:41–66` — сам поиск: перебор гексов с линейным выбором лучшего из списка, на каждый
  гекс — проверка всех островков и соседей соседей;
- `pages/WorldGL.tsx:117` и `:150–176` — при новой сцене все буферы видеокарты выбрасываются и загружаются заново;
  `pages/RoutesGL.tsx:31`, `:49–53` — то же для морских путей.

**Что не так:** запоминание в `TeamMap` привязано к «тому же самому объекту в памяти», а после каждого ответа сервера
и каждой разницы все части карты — новые объекты, даже если в них ничего не изменилось. Берег, островки, дно и маска
тумана защищены ключом по содержимому (`lib/keep.ts`) и не пересчитываются — а морские пути, сцена мира и подписи не
защищены. По профилю соседа поиск морских путей при открытии карты занимает суммарно около 0,3–0,4 с на быстром процессоре
(`seaRoute.js` 219 мс, `isletRadiusAt` 90 мс, ключи гексов ещё ~50 мс). То же самое повторяется **каждую минуту** и
после каждого события; на слабом телефоне это секунда-полторы, в которую карта стоит.

**Как лучше:**
1. Морские пути — в такую же память заготовок, как берег и островки: ключ `гексы | от | до`.
   ```ts
   const SEA = new Map<string, Pt[]>();
   const seaPath = (hexKey: string, from: string, to: string, ...) =>
     keep(SEA, `${hexKey}|${from}|${to}`, () => routeCurve(seaRoute(...), ...));
   ```
   Путь между двумя узлами не меняется, пока не меняются гексы суши, — считать его второй раз незачем.
2. При получении новой карты оставлять прежние части там, где содержимое не изменилось («общие части»):
   ```ts
   function reuse<T extends object>(prev: T | null, next: T): T {
     if (!prev) return next;
     const out = { ...next } as Record<string, unknown>;
     for (const k of Object.keys(next)) {
       const a = (prev as any)[k], b = (next as any)[k];
       if (a !== b && typeof b === "object" && JSON.stringify(a) === JSON.stringify(b)) out[k] = a;
     }
     return out as T;
   }
   // setMap((prev) => reuse(prev, m));
   ```
   Сравнение всей карты строками — около 2 мс (у соседа: `JSON.stringify` карты 2,0 мс), зато всё запоминание в
   `TeamMap` начинает работать: если за минуту ничего не изменилось, не пересчитывается ничего.
3. В `onMapPush` убрать двойную копию: либо `applyPatch(structuredClone(cur), patch, true, true)`, либо без
   `structuredClone` — и после применения пропустить результат через тот же `reuse`.
4. `positions` (`TeamMap.tsx:177`) — зависимость от `map.revealed` и `map.edges`, а не от всего `map`.
5. В `WorldGL` разделить сцену на неизменную часть (гексы, берег) и изменчивую (стороны, картинки) и перезагружать
   только ту, что изменилась (см. также C6).

**Что это даст:** исчезает подвисание раз в минуту и после каждого события игры (оценка: 0,3–0,4 с на быстром
процессоре, 1–1,5 с на слабом телефоне — по замеру соседа при открытии, та же работа). Возврат в приложение из
другой программы перестаёт дёргать карту.

**Объём работы:** малый (пункты 1, 3, 4), средний (пункты 2, 5).

**Риск:** низкий для п. 1 (ключ должен включать состав гексов и островков — как у остальных заготовок). Для п. 2:
сравнение строками чувствительно к порядку полей — сервер отдаёт один и тот же порядок, но нужен тест.

#### A3. Даты: форматтер создаётся заново на каждый вызов, а вызовов — сотни в секунду

**Где:**
- `lib/format.ts:21–24` (`dayKey`) и `:28–41` (`fmtDate`): на одну дату до шести обращений к `toLocaleDateString` /
  `toLocaleTimeString` с параметрами — каждое создаёт внутри браузера новый форматтер дат;
- `packages/domain/src/fireworks.ts:10–13` (`localDay`) — `new Intl.DateTimeFormat(...)` на каждый вызов;
- `pages/FireworksLayer.tsx:91–95` — раз в секунду `fireworksUntil` для каждого взятого города (два `localDay` на город);
- вызывается из списков: `pages/Journal.tsx:198` (каждая запись летописи), `pages/TeamMap.tsx:625` (каждая метка
  команды — внутри подписей карты, которые пересобираются раз в секунду, см. A1), `pages/TeamPage.tsx` — десятки мест.

**Что не так:** создание форматтера дат — одна из самых медленных операций в браузере (десятки микросекунд на
компьютере, сотни на телефоне). Здесь она выполняется по 5–6 раз на каждую дату, а даты пересчитываются каждую
секунду из-за A1. По профилям соседа: `format.ts` — 342 мс за 32 с перетаскивания и 335 мс за 18 с с открытыми
разделами; `localDay` салюта — 163 и 88 мс. В сценарии перетаскивания это первые две строки среди кода приложения, в сценарии с разделами — первая и четвёртая.

**Как лучше:**
```ts
const FMT = new Map<string, Intl.DateTimeFormat>();
function fmt(loc: string, tz: string | undefined, o: Intl.DateTimeFormatOptions) {
  const k = `${loc}|${tz ?? ""}|${JSON.stringify(o)}`;
  let f = FMT.get(k);
  if (!f) { f = new Intl.DateTimeFormat(loc, { ...o, timeZone: tz }); FMT.set(k, f); }
  return f;
}
```
`dayKey` и `fmtDate` берут готовый форматтер. Ключи «сегодня» и «вчера» считать один раз в минуту, а не на каждую дату.
В `localDay` — тот же приём (форматтер на пояс); в салюте день взятия города посчитать один раз на город (он не
меняется), а «сегодня» — один раз на проверку.

**Что это даст:** форматирование дат дешевеет в 10–30 раз (оценка). Вместе с A1 уходит главный потребитель
процессора среди кода приложения в покое и при открытых списках.

**Объём работы:** малый.

**Риск:** низкий. Память форматтеров сбрасывать не нужно: вариантов — десяток. Проверить переход через полночь
(«сегодня» → «вчера») и смену пояса игры (`setDisplayTimeZone`).

- `pages/TeamMap.tsx:160–165` — таймер «раз в две секунды перерисовать карту» работает, пока в ответе есть хоть один
  починенный или затонувший корабль, то есть и после того, как их анимация давно кончилась (`:675` — корабль уже не
  рисуется, а таймер идёт).

**Что не так:** три мелких, но постоянных источника лишней работы на главном экране.

**Как лучше:** `worldBody` считать только при `!glWorld`; сцену разделить на «неизменное» (гексы, берег — от ключа
гексов) и «изменчивое» (стороны, картинки), цвета песка и мокрой кромки передавать в `WorldGL` отдельно, без
пересборки геометрии; таймер кораблей останавливать, когда у всех кораблей прошло 10 секунд после починки или гибели.

**Что это даст:** нажатие на дело отзывается без пересборки мира (оценка: минус 5–30 мс на слабом телефоне на
каждое нажатие); карта не перерисовывается раз в две секунды без нужды.

**Объём работы:** малый.

**Риск:** низкий.

### B. Открытие карты

#### B1. Обводка городов: расстояния считаются в коде при загрузке каждой картинки

**Где:** `pages/WorldGL.tsx:55–95`, сам расчёт — `:66–78`; память текстур — `:138–139`, очистка — только при уходе
с карты (`:243`).

**Что не так:** для обводки города цветом команды нужна карта расстояний до картинки. Она считается так: 24 прохода
по квадрату 512×512, в каждом проходе у каждой пустой точки проверяются 9 соседей — около 45 миллионов проверок на
картинку, на главном потоке, в момент, когда картинка загрузилась. Картинок — по числу видов городов на карте плюс
старт (до десяти), и ещё раз для каждого времени суток. Для картинки старта расчёт делается тоже, хотя обводки у неё
нет. По профилю соседа это **самая дорогая функция при открытии карты: 796 мс** на быстром процессоре; на слабом
телефоне — 2,5–4 секунды (оценка), кусками по 0,2–0,5 с, в каждом из которых карта не слушается.
Текстуры прежних времён суток не выбрасываются: за день открытой карты копится до четырёх наборов (оценка: до 60 МБ
памяти видеокарты).

**Как лучше:**
1. Тот же результат — двумя проходами вместо двадцати четырёх (классический «двухпроходный» расчёт расстояний;
   для расстояния «как ходит король» он точный):
   ```ts
   // d = 0 у непрозрачных точек, иначе MAX_D + 1
   for (let y = 0; y < P; y++) for (let x = 0; x < P; x++) {           // сверху вниз
     const i = y * P + x; let v = d[i];
     if (x > 0) v = Math.min(v, d[i - 1] + 1);
     if (y > 0) { v = Math.min(v, d[i - P] + 1); if (x > 0) v = Math.min(v, d[i - P - 1] + 1); if (x < P - 1) v = Math.min(v, d[i - P + 1] + 1); }
     d[i] = v;
   }
   // и зеркально снизу вверх; в конце значения больше MAX_D → 255
   ```
   Это около 2 миллионов операций вместо 45 — в 20 раз быстрее. Считать только в прямоугольнике картинки с полями
   (до 368×368), а не во всём квадрате 512×512.
2. Не считать для картинок без обводки (старт).
3. Хранить результат по адресу картинки вне компонента (как берег и островки): при повторном входе на карту
   считать не придётся.
4. Лучший вариант — посчитать карту расстояний заранее, при подготовке картинок (`scripts/`), и положить рядом
   второй маленькой картинкой: тогда в браузере расчёта нет совсем.
5. При смене времени суток удалять текстуры, которых больше нет в сцене.

**Что это даст:** карта начинает слушаться пальца раньше — на 0,8 с на быстром процессоре (замер соседа), на
секунды на слабом телефоне.

**Объём работы:** малый (п. 1–3, 5), средний (п. 4).

**Риск:** низкий. Обводка должна совпасть пиксель в пиксель — проверяется имеющимися эталонными снимками
(`scripts/map-shots.mjs`, `scripts/map-shots-diff.py`).

#### B2. Догон живности: до 18 000 шагов мира при открытии карты и возврате в приложение

**Где:** `pages/Fauna.tsx:1134` (эпоха 900 с, шаг 0,05 с), `:2083–2097` (`sync`), `:2131–2136` (догон кусками по
30 мс через `setTimeout(…, 0)`), `:2140`; цена шага — `:1168–1197`, в том числе `:1171` (список препятствий заново
на каждый шаг), `:1190` (новый массив судов на каждый шаг), `:60–77` (`landPen`: семь строк-ключей `"q,r"` на вызов,
до четырёх вызовов на каждого зверя и корабль).

**Что не так:** звери у всех игроков одинаковые, поэтому мир «проматывается» от начала пятнадцатиминутной эпохи до
текущей секунды: в среднем 9 000 шагов, в худшем 18 000. Куски по 30 мс идут подряд, пауза между ними — доли
миллисекунды: главный поток занят почти сплошь, кадры идут не чаще 30 в секунду, палец отзывается с задержкой.
То же при каждом возврате в приложение (догоняются секунды отсутствия). По профилю соседа при открытии карты
`Fauna.tsx` занял 454 мс, из них `landPen` — 152 мс; на слабом телефоне — 1,5–2,5 с (оценка).

**Как лучше:**
1. Сделать шаг дешевле, не меняя его результат: ключи суши — числами, а не строками
   (`(q + 512) * 1024 + (r + 512)` в `Set<number>`); список препятствий пересчитывать только при смене списка кораблей;
   массив судов не создавать на каждом шаге. Оценка: в 2–3 раза быстрее.
2. Догон — вежливее: кусок 8–10 мс, следующий — через `requestIdleCallback` (или `scheduler.postTask` с приоритетом
   `background`), а пока идёт жест — не догонять вовсе. Дольше по часам, но карта при этом слушается.
3. Дальний вариант — этап Э5 из `docs/proposals/map-gpu.md` (расчёт мира в фоновом потоке): тогда главный поток
   свободен совсем.

**Что это даст:** первые секунды на карте и возврат в приложение — без рывков.

**Объём работы:** малый (п. 1–2), большой (п. 3).

**Риск:** п. 1 — звери должны остаться на тех же местах: есть тест `fauna.test.ts`, его достаточно дополнить
сравнением положений до и после правки. П. 2 — звери «всплывут» на карте чуть позже (сейчас они тоже появляются
только после догона).

#### B3. Дно моря, маска тумана и плитки облаков — тяжёлые расчёты одним куском

**Где:**
- `pages/Seabed.ts:26–61` (цикл `:46–58`): поле 384×~384 точек, для каждой — расстояние до каждого гекса суши и
  каждого островка (около 40 миллионов `Math.hypot`); по профилю соседа — 265 мс;
- `pages/MapLayers.tsx:266–354` (`buildFogMask`): холст до 2,5 мегапикселя (`:272`) и до шести вспомогательных
  холстов; вызывается внутри перерисовки (`:396`) при каждом изменении тумана;
- `lib/noise.ts:17–29`, `:51–62`, `:127–129`: шум и три плитки облаков 512×512 по точке в коде; по профилю — 96 мс.

**Что не так:** всё это выполняется прямо во время перерисовки React, одним куском. На главной странице есть
заготовка в простое (`pages/mapWarm.ts:14–27`) — она спасает, если человек идёт через «Мои игры»; при входе по

**Как лучше:** дно — искать расстояние только до ближних гексов (разложить сушу по крупной сетке; или тот же
двухпроходный расчёт расстояний, что в B1); на телефоне хватит поля 256 вместо 384. Маску тумана строить не в
перерисовке, а следом за ней (в эффекте), показывая прежнюю маску до готовности новой.

**Что это даст:** минус 0,3–0,4 с на быстром процессоре при входе на карту без заготовки (замер соседа),
на слабом телефоне — секунда-полторы (оценка).

**Объём работы:** средний.

**Риск:** дно — вид моря у берегов должен совпасть (сравнить картинку поля до и после); маска — на один кадр
дольше держится прежний туман.

#### C1. Берег в WebGL: 28 проходов на кадр, плотность до трёх

**Где:** `pages/WorldGL.tsx:196–201` (песок: одна сплошная полоса, двенадцать полупрозрачных и мокрая кромка — 14
вызовов, каждый с трафаретом), `lib/glLines.ts:132–136` (с трафаретом каждый вызов — два прохода), `:26–46`

**Что не так:** при каждом движении карты вся линия берега рисуется 28 раз широкими полосами, которые перекрывают

приближении занимает до трети экрана (оценка).

в шейдере — той же суммой двенадцати слоёв, заранее сведённой в маленькую таблицу (текстуру из 64 значений). Два
прохода вместо двадцати восьми. Либо рисовать берег во временную картинку раз на устоявшийся вид (как уже сделано
для гексов местности, `MapLayers.tsx:577–612`) и при перетаскивании только сдвигать её.

**Что это даст:** плавнее перетаскивание и щипок на слабых видеокартах. **Оценка, нужен замер:** на телефоне
открыть `?perf=1&gloff=coast` (выключатель уже есть, `WorldGL.tsx:34–35`) и сравнить строку «жест» с обычным режимом.
Если разницы нет — пункт снять.

**Объём работы:** средний.

**Риск:** край песка должен совпасть с нынешним — проверка эталонными снимками; сглаживание может отличаться
в пределах одного пикселя.

#### C2. Слой подписей: всё лежит в странице, стили пересчитываются на каждом шаге масштаба

**Где:** `pages/TeamMap.tsx:461–641` (все подписи, точки, метки дел — для всей карты, без отсечения невидимого),
`:345–347` (у каждого элемента `scale(var(--inv))`), `pages/MapLayers.tsx:115` и `:121–155` (слой размером
1,8×1,8 экрана; переменные `--k`, `--inv`, `--inv-mark` меняются каждые 120 мс жеста), `styles/player.css:9`

и заново рисует слой площадью в три с лишним экрана. В плане `docs/proposals/map-gpu.md` это этап Э4 («Верхний SVG
легче») — он не сделан.

**Как лучше:** сделать Э4: при фиксации вида отдавать в разметку только элементы, попадающие в отрисованную область
с запасом; обёртке дать `contain: layout paint style`. Запас слоя (`PAD = 0.4`) можно уменьшить до 0,25, как у гексов
и берега: площадь слоя упадёт с 3,2 до 2,25 экрана.

**Что это даст:** дешевле каждый шаг масштаба и каждая фиксация вида на картах с сотней подписей; меньше памяти.

**Объём работы:** средний.

**Риск:** у края экрана подпись может появиться с опозданием на одну фиксацию — подобрать запас; проверка снимками.

#### C3. Огонь приоритетного дела — анимация внутри большого слоя подписей

**Что не так:** анимация частей SVG, в отличие от анимации обычных блоков, в Safari целиком идёт через главный поток

**Что это даст:** в покое главный поток свободен; меньше расход батареи.

#### C4. Стороны в WebGL: пройденные рисуются по одной, по 2–3 вызова на сторону

**Где:** `pages/WorldGL.tsx:165–172` (сторона с подложкой или чужими отрезками — отдельный буфер), `:205–212`

буферы, а не загрузка каждый кадр.

**Что это даст:** время кадра мира перестаёт расти с числом пройденных сторон. **Оценка, нужен замер:** строка
«мир (gl)» в `?perf=1` на тяжёлой партии стенда.

#### C5. Шторм и смена времени суток пересобирают мир и плитки тумана

**Где:**
- `pages/TeamMap.tsx:134–135` — освещение шторма (`stormLight`) считается при каждой перерисовке заново и каждый раз
  даёт новый объект; у администратора то же сделано правильно, через `useMemo` (`pages/AdminMap.tsx:171–172`);
- `pages/TeamMap.tsx:397` — `light` в зависимостях сцены мира: новый объект света → вся сцена заново → все буферы
  заново (`pages/WorldGL.tsx:150–176`);
- `lib/daytime.ts:166–183` — доля шторма меняется около 12 раз в секунду три секунды подряд;
- `pages/MapLayers.tsx:248–252` и `lib/noise.ts:51–62` — при любом изменении цвета тумана три плитки 512×512
  пересчитываются по точке в коде;
- `lib/daytime.ts:133` — в получасовом окне перехода (четыре раза в сутки) свет меняется каждые 30 секунд;
  `pages/MapLayers.tsx:25`, `:558`, `:623` и `pages/Islets.tsx:63`, `:159` — слои местности и островов при этом
  полностью пересоздаются: новые объекты картинок, новый запасной растр, размытие берега заново.

**Что не так:** пока идёт шторм, каждая перерисовка (а они ежесекундные, A1) пересобирает мир для видеокарты.
На входе в шторм и выходе из него три секунды подряд пересчитываются плитки тумана — это видимый рывок как раз
в самый зрелищный момент. В переходе дня и ночи — рывок раз в 30 секунд в течение получаса.

**Как лучше:** `const light = useMemo(() => storm.t > 0 ? stormLight(dt.light, storm.t) : dt.light, [dt.light, storm.t])`;
цвета песка и кромки — в `WorldGL` мимо геометрии (через `ref`, как свет у моря); плитки тумана хранить одной
прозрачностью и красить средствами холста (заливка цветом через `source-in` — миллисекунда вместо цикла по точкам);
в слоях местности и островов картинки и растр держать между сменами света, а долю перехода передавать через `ref`
и просто помечать слой «перерисовать».

**Что это даст:** плавный вход в шторм и выход из него; нет рывков раз в 30 секунд на закате и рассвете.

**Объём работы:** малый (свет и плитки), средний (слои местности и островов).

**Риск:** цвета тумана и берега в шторм должны совпасть с нынешними — сравнить кадры `?storm=1` и `?tod=18:05`.

#### C6. Туман: окна разведки вырезаются заново на каждом кадре

**Где:** `pages/MapLayers.tsx:446–461` (на каждое видимое окно — основной круг и девять «клубов», для каждого

### D. Листы и окна

#### D1. «Стекло» над живой картой: карта не замирает под листами

**Где:**
- размытие: `styles/theme.css:101` (любой лист — `blur(18px) saturate(1.05)`), `styles/theme-player.css:20` (панель
  раздела), `:314` (шапка панели — ещё одно размытие внутри уже размытой панели), `:298` (кнопки шапки и часики),
  `styles/player.css:1033` (пять плиток панели разделов);
- размеры: `styles/player.css:1027` (панель раздела на телефоне — весь экран без верхних 64 px),
  `styles/components.css:192` (листы города, корабля, каменоломни — 92 % высоты экрана);
- циклы слоёв не знают, что карта закрыта: `pages/SeaGL.tsx:181–187` (30 кадров в секунду), `pages/MapLayers.tsx:465–475`
  (туман, 24), `pages/Fauna.tsx:2137–2143` (живность, 24, три холста), `pages/Lakes.tsx:120–125` (озёра, 30).

**Что не так:** размытие подложки браузер считает заново каждый раз, когда под стеклом что-то изменилось. Под
стеклом — карта, которая меняется 24–30 раз в секунду. Значит, пока игрок читает дело, решает задания города или
листает «Летопись», видеокарта непрерывно рисует воду, туман и зверей, которых почти не видно, и столько же раз
размывает до 92 % экрана радиусом 18 px. На слабых телефонах это отнимает кадры у прокрутки самого листа и греет
телефон. В покое на карте работают ещё девять маленьких стёкол (плитки панели, кнопки шапки).

**Как лучше (вид тот же):**
1. Общий признак «карта закрыта листом» — и все циклы слоёв его читают:
   ```ts
   // lib/mapActivity.ts
   let covered = false;
   export const setMapCovered = (v: boolean) => { covered = v; };
   export const mapCovered = () => covered;
   // в цикле слоя: if (!dirty && (still || mapCovered() || now - last < 33)) return;
   ```
   `TeamPage` ставит признак, когда открыта панель раздела или большой лист (город, корабль, каменоломня, дело).
   Слои продолжают рисовать при движении карты и при смене данных, но не «дышат» сами. Размытая картинка под
   стеклом перестаёт меняться — браузер перестаёт её пересчитывать.
   Вариант мягче: под листом не останавливать, а рисовать 2–4 раза в секунду.
2. Размытие у шапки панели (`theme-player.css:314`) снять, если под ней ничего не прокручивается: она лежит
   внутри панели, у которой размытие уже есть, — второй проход ничего не добавляет (проверить глазами).
3. Заодно свести циклы слоёв к одному общему «метроному»: сейчас у каждого слоя свой `requestAnimationFrame`,
   десять штук, и выключить их разом негде.

**Что это даст:** листы и списки листаются плавно, телефон меньше греется и разряжается. **Оценка, нужен замер
на настоящем телефоне:** открыть лист города и сравнить частоту кадров при прокрутке с `?perf=1` и с
`?perf=1&perfoff=sea,fog,fauna` (слои выключены — это и есть потолок выигрыша).

**Объём работы:** малый (п. 1–2), средний (п. 3).

**Риск:** вода под матовым стеклом перестанет шевелиться. Под размытием 18 px и подложкой 55 % движение почти не
различимо, но это видимая вещь — показать владельцу образцом «с паузой / без паузы / 3 кадра в секунду» и взять его
слово. У маленьких листов (метка, «Край тумана») карта видна рядом с листом — для них паузу не включать.

#### D2. Мёртвый обработчик касаний, который мешает прокрутке

**Где:** `pages/TeamPage.tsx:353–364` (обработчик `touchmove` на весь экран карты с `{ passive: false }`),

**Объём работы:** малый.

**Риск:** низкий; проверить, что свайп влево по-прежнему закрывает панель раздела, а полосы вкладок листаются.

### F. Память и утечки

#### F1. Слои и память: 10–12 холстов во весь экран, четыре контекста WebGL, слой подписей в три экрана

**Где (плотность холста — множитель к размеру экрана):** море `pages/SeaGL.tsx:162` (0,55–0,7), острова и берег
`pages/Islets.tsx:73` (до 2), местность `pages/MapLayers.tsx:565` (до 1,5, плюс запасной растр `:577–583`), озёра
`pages/Lakes.tsx:103` (до 1,25), мир `pages/WorldGL.tsx:130` (**до 3**, с трафаретом), туман `pages/MapLayers.tsx:409`
(до 1,25, плюс маска до 2,5 мегапикселя `:272`), живность `pages/Fauna.tsx:2058–2060` (до 2, **три холста**), морские
пути `pages/RoutesGL.tsx:44` (до 2), салют `pages/FireworksLayer.tsx:29`, шторм; слой подписей — `pages/MapLayers.tsx:115`
(1,8×1,8 экрана) с `will-change: transform` (`styles/player.css:9`). Память масок тумана — до шести штук
(`lib/keep.ts:6`, `pages/MapLayers.tsx:260`).

**Что не так:** на телефоне 390×844 с тройной плотностью это, по моей прикидке, 100–150 МБ графической памяти:
мир — около 12 МБ (вдвое с буфером показа), три холста живности — 16 МБ, слой подписей — до 38 МБ, маски тумана —
до 10 МБ каждая (до 60 МБ в памяти заготовок), плюс остальное. Четыре отдельных контекста WebGL — это четыре набора
служебной памяти видеокарты. На телефонах с 2–3 ГБ памяти система при переключении в другую программу выгружает
такие вкладки — и по возвращении приложение грузится заново. Это вероятная причина «подгрузок». **Оценка, нужен
замер:** `chrome://inspect` → Memory, или диспетчер задач браузера на телефоне.
Кроме того, три холста живности очищаются и рисуются 24 раза в секунду, даже когда на «небе» и «палубе» ничего нет
(`pages/Fauna.tsx:2103–2128`).

**Как лучше:**
- мир: плотность не выше 2 (при тройной — отличие в резкости тонких линий на глаз не различимо, но это вид —
  показать владельцу рядом);
- живность: не очищать и не рисовать холст, на котором в прошлом и этом кадре пусто; в перспективе — два холста
  вместо трёх;
- слой подписей: запас 0,25 вместо 0,4 (см. C2);
- память масок тумана — 2 штуки вместо 6 (текущая и предыдущая);
- дальний вариант: море, озёра, мир и пути — в одном контексте WebGL (большой объём; делать только если замер
  покажет нехватку памяти).

**Что это даст:** приложение реже выгружается из памяти; меньше работы видеокарте на сведение слоёв.

**Объём работы:** малый (первые четыре пункта), большой (один контекст).

**Риск:** плотность мира — видимая вещь, только с образцом; остальное невидимо.

## 4. Что сделано хорошо — не трогать

- **Перемещение карты** (`lib/useViewport.ts`): вид лежит в `ref` и рассылается подписчикам, React узнаёт о нём только
  в конце жеста; слои двигаются трансформацией. Это правильная схема, менять её не нужно.
- **Мир, море, озёра, морские пути на WebGL**: геометрия загружается один раз, в кадре меняются только масштаб и
  сдвиг; невидимое отсекается по рамке; кадр рисуется только по признаку «изменилось»; при потере контекста — возврат
  к прежнему способу. Море считается в пониженном разрешении и 30 раз в секунду, а не 60.
- **Память заготовок** (`lib/keep.ts`, `pages/mapWarm.ts`): берег, островки, дно и маска тумана считаются один раз
  на игру и ещё заранее, в простое, пока человек на главной.
- **Запасные растры местности и берега** (`TilesLayer`, `IsletsLayer`): при перетаскивании сдвигается готовая
  картинка, заново рисуется только когда вид устоялся.
- **Нажатия считает код** (`lib/mapHit.ts`), а не невидимые широкие линии в SVG — минус сотни элементов.
- **Все циклы стоят при скрытой вкладке** (`document.hidden`) и уважают настройку «уменьшить движение».
- **Свой измеритель**: `?perf=1`, выключатели слоёв `perfoff=` и `gloff=`, эталонные снимки, отправка замеров
  с устройств (`lib/perf.ts`) — этим и надо мерить всё перечисленное выше.
- **Сначала оболочка, потом карта** (`pages/TeamPage.tsx:176–177`): экран отзывается сразу, карта приходит следом.
- **Склейка перечитываний** (`lib/useGameEvents.ts:34–44`) и карта разницей — сама идея верная, чинить нужно только
  то, что после разницы всё считается новым (A2).
- **Летопись порциями по 60**, аватарки — уменьшенные копии с отложенной загрузкой, у картинок в списках заданы
  размеры: скачков раскладки не нашёл.
- **Состав команды** тикает раз в 30 секунд своим таймером внутри себя (`pages/TeamPage.tsx:1287–1288`) — так и
  должны быть устроены все часы (A1).
