# Ревизия B. Загрузка данных и сборка сайта «Земли Слова»

Что проверено: `apps/web` (исходники, готовая сборка `apps/web/dist` от 15.11 19:39, коммит `1405db53`), выдача статики в `apps/api/src/app.ts`, `deploy/caddy/Caddyfile`, `Dockerfile`. Ничего не менялось и не пересобиралось; на боевой сайт и стенд не ходил.

Пометки у чисел: **замер** — измерено по файлам сборки и `public/`; **видно из кода** — следует из прочитанных строк; **оценка** — прикидка, которую надо подтвердить (чем — сказано в разделе 6).

Термины в двух словах:
- **gzip** — сжатие при передаче; «КБ gzip» — сколько реально едет по сети.
- **сервис-воркер (SW)** — программа-посредник в браузере, которая держит копию сайта на телефоне (то, что делает сайт приложением-PWA).
- **ленивая загрузка** — кусок программы скачивается не сразу, а когда понадобился.
- **SSE** — постоянное соединение, по которому сервер сам присылает события («кто-то сдал дело»).
- **опрос (polling)** — запрос по таймеру «нет ли нового».
- **водопад запросов** — запросы идут друг за другом: второй ждёт ответа первого.

## 1. Главное

Задел сделан хороший: есть память готовых ответов (`ready` / `apiReady` / `prefetch`), карта команды приходит по SSE маленькими разницами, картинки кэшируются на месяц, оболочка открывается из кэша телефона. Но поверх этого накопилось пять вещей, которые и дают «долго», «подгрузки» и «подвисания»:

1. **Главный файл программы — 1 885 КБ (562 КБ gzip), и 43 % в нём не нужны русскому игроку вовсе**: английский перевод (633 КБ) и тексты «Что нового» (182 КБ). Ещё около 250 КБ — экраны администратора. Каждая выкладка заставляет каждый телефон перекачать всё заново (0,83 МБ gzip), включая библиотеку графиков администратора.
2. **От значка до карты — три круга запросов подряд и три разных экрана загрузки** («Загрузка…» → заготовка главной → «Загружаем карту…»). Между запусками ничего не помнится, хотя прошлую карту можно показать мгновенно.
3. **Карта команды перечитывается целиком слишком часто** (раз в минуту, второй минутный таймер шторма, после каждого своего действия дважды, при возврате в приложение) — и каждый раз вся карта пересчитывается заново, даже если ничего не изменилось. Это самый вероятный источник периодических подвисаний.
4. **Карточка города открывается «лесенкой»**: заглушка шапки → данные города → ещё 3 запроса → ещё 1. Кэша нет, четыре из пяти запросов нужны свёрнутым разделам.
5. **Шрифты при каждом запуске перепроверяются по сети**, поэтому текст сначала рисуется запасным шрифтом, потом «перещёлкивается».

Всё перечисленное лечится без изменения внешнего вида и правил. Большая часть — малые и средние правки.

## 3. Все находки

### А. Сборка

#### Н1. Английский перевод и «Что нового» лежат в главном файле программы
**Где:** `apps/web/src/lib/i18n.tsx:6` (`import { EN } from "./i18n.en"`), `apps/web/src/lib/i18n.en.ts:1-9` (шесть словарей склеиваются в один), `apps/web/src/main.tsx:26` и `apps/web/src/pages/WhatsNewPage.tsx:5` (`CHANGELOG`), `apps/web/src/content/changelog.ts` (186 КБ), `apps/web/src/lib/en/changelog.ts` (292 КБ).

**Что не так:** функция перевода `t()` подключает словарь напрямую, поэтому весь английский словарь попадает в главный файл и скачивается, разбирается и держится в памяти у всех, включая русских игроков. Отдельно: страница «Что нового» подключена обычным образом, и её тексты за два месяца (186 КБ) плюс их перевод (292 КБ, причём ключ перевода — та же русская строка, то есть русский текст лежит в файле дважды) тоже в главном файле.

Замер по готовой сборке (`dist/assets/index-BOlyANRd.js`, границы найдены по первой и последней строке словарей):

| Часть главного файла | Размер | gzip | Доля |
|---|---|---|---|
| Библиотеки (React, роутер) | 236 КБ | 76 КБ | 12,5 % |
| **Английский словарь** | **633 КБ** | **188 КБ** | **33,6 %** |
| Код игры (все экраны) | 824 КБ | 250 КБ | 43,7 % |
| **«Что нового» (русский текст)** | **182 КБ** | **45 КБ** | **9,6 %** |
| Итого | 1 885 КБ | 562 КБ | |

**Как лучше:**
1. Словарь грузить лениво и только тем, у кого язык английский:
```ts
// i18n.tsx
let EN: Record<string, string> | null = null;
export async function loadEn() { if (!EN) EN = (await import("./i18n.en")).EN; }
export function t(ru, vars) { const base = current === "en" ? EN?.[ru] ?? ru : ru; … }
```
В `AuthProvider` флаг `loading` снимать, когда пришёл и ответ `/api/auth/me`, и словарь (если язык `en`) — тогда англоязычный игрок не увидит русского текста. Язык последнего входа запомнить в `localStorage`, чтобы словарь начинал качаться одновременно с `/me`.
2. Страницу «Что нового» сделать ленивой (`import("./pages/WhatsNewPage")`), перевод её текстов (`en/changelog.ts`) — отдельным файлом, который подключается вместе с этой страницей.

**Что это даст:** главный файл 1 885 → ~1 070 КБ, по сети 562 → ~330 КБ gzip (**замер** частей). Меньше разбора программы при каждом холодном запуске и ~1,5 МБ строк меньше в памяти телефона.
**Объём работы:** малый–средний (полдня с проверкой английского языка).
**Риск:** низкий. Проверить: вход англоязычным, смена языка на странице входа, страница «Что нового» на двух языках.

#### Н2. Экраны администратора и редкие страницы — в главном файле; библиотеки не вынесены
**Где:** `apps/web/src/main.tsx:7-28` — все страницы подключены обычными `import`, лениво только `AdminDashboard` (строка 20) и `GameAnalytics` (`GamePage.tsx:94`). `apps/web/vite.config.ts:34` — нет настройки разбиения (`manualChunks`).

**Что не так:** игрок скачивает и разбирает страницу игры администратора со всеми разделами (`GamePage`, `AdminMap`, `SettingsBlock`, `DeedsBlock`, `TeamsBlock`, `SubmissionsBlock`, `BattlesBlock`, `StartBlock`, `FinishBlock`, `RecipientsBlock`, `VisitsBlock`, `AdminsBlock`, `WallsBlock`, `AdminUsersPage`, `SupportPage`, `AllGamesPage`, `LabelsPage`, `TaskReport`) — около **250 КБ** после сжатия имён (**оценка**: каждый файл отдельно пропущен через минификатор, без записи в репозиторий). Гостевые и редкие страницы (инструкция, ролик-знакомство, вход, восстановление пароля, аккаунт, политика) — ещё около **85 КБ** (**оценка**).
Второе: React и роутер (236 КБ) лежат в том же файле, что и код игры, поэтому при любой правке кода их имя-хэш меняется и они качаются заново.

**Как лучше:**
- `GamePage` с разделами, страницы суперадмина, `HowToPlayPage` + `IntroStory`, `AccountPage`, `PrivacyPage` — ленивыми. Чтобы не было мигания заглушки (замечание из `GamePage.tsx:61`: «React.lazy на миг показывает запасной вид»), использовать обёртку, которая рисует сразу, если файл уже скачан, и качать файл заранее в простое: администратору — как только `/api/games` вернул его игры, игроку — не качать вовсе.
```ts
function lazyEager<P>(load: () => Promise<{ default: ComponentType<P> }>) {
  let C: ComponentType<P> | null = null, p: Promise<void> | null = null;
  const preload = () => (p ??= load().then((m) => { C = m.default; }));
  const W = (props: P) => { if (!C) throw preload(); return <C {...props} />; }; // Suspense ждёт только в первый раз
  return Object.assign(W, { preload });
}
```
- В `vite.config.ts`: `build.rollupOptions.output.manualChunks = { vendor: ["react", "react-dom", "react-router-dom"] }` — библиотеки в отдельный файл с постоянным именем.

**Что это даст:** у игрока код игры 824 → ~480 КБ (**оценка**). Вместе с Н1 главный файл игрока ≈ 480 КБ + библиотеки 236 КБ ≈ **720 КБ вместо 1 885 КБ**, по сети ≈ **220–240 КБ gzip вместо 562**. Библиотеки (76 КБ gzip) перестают перекачиваться при выкладках.
**Объём работы:** средний (день: разбиение, заглушки, проверка переходов).
**Риск:** средний — ленивые файлы после выкладки меняют имена; нужна страховка «не удалось скачать кусок → перезагрузить страницу» и правка Н28.

#### Н3. Графики администратора (618 КБ) качаются всем; каждая выкладка — перекачка всего
**Где:** `apps/web/vite.config.ts:18` (`globPatterns: ["**/*.{js,css,html,ico,webmanifest}", …]` — в предзагрузку SW попадают все файлы JS), `apps/web/vite.config.ts:7` (`__BUILD_ID__: Date.now()`), готовый `dist/sw.js` (список предзагрузки), начало `dist/assets/Chart-jsC1-nyy.js` (`import … from "./index-BOlyANRd.js"`).

**Что не так:**
- В списке предзагрузки сервис-воркера — `Chart-…js` (библиотека графиков ECharts, 618 КБ / 207 КБ gzip), `AdminDashboard`, `GameAnalytics`. Их скачивает телефон **каждого игрока**, хотя открыть их может только администратор. **Замер:** предзагрузка — 16 файлов, 3,09 МБ, по сети ~1,13 МБ при первой установке.
- Файл графиков ссылается на главный файл по имени с хэшем, а главный файл меняется при каждой сборке (в него вшит `__BUILD_ID__` — время сборки; он нужен только картинкам инструкции, `HowToPlayPage.tsx:20`). Значит, при каждой выкладке меняются имена **всех** файлов JS, и каждый телефон перекачивает ~0,83 МБ gzip (**замер**: 562 + 207 + 46 + мелочь), даже если поправлена одна подпись.

**Как лучше:**
- В `workbox`: `globIgnores: ["**/Chart-*.js", "**/AdminDashboard-*.js", "**/GameAnalytics-*.js", …]` (и будущие админские и английские куски) плюс правило `runtimeCaching` для `/assets/*.js|css` со стратегией `CacheFirst` (имена с хэшем, содержимое не меняется) — куски кэшируются у того, кто ими пользуется.
- `__BUILD_ID__` убрать из главного файла: метку картинок инструкции брать из хэша самих картинок или вынести инструкцию в ленивый файл (тогда метка меняет только его).
- Библиотеки — отдельным файлом (Н2).

**Что это даст:** выкладка стоит телефону игрока ~200 КБ gzip вместо ~830 КБ (**оценка** после Н1–Н3). На мобильном интернете это разница между «обновилось незаметно» и «минуту качает в фоне, мешая игре».
**Объём работы:** малый (час-два) для `globIgnores`; вместе с Н2 — в тот же день.
**Риск:** средний, тот же, что в Н2 (старое имя куска после выкладки) — лечится Н28 и страховкой перезагрузки.

#### Н4. Нет заранее сжатых файлов (brotli)
**Где:** `deploy/caddy/Caddyfile:7` (`encode gzip zstd` — сжатие «на лету» при каждой отдаче), `apps/api/src/app.ts:116-123`.

**Что не так:** Caddy сжимает 1,9 МБ JS заново на каждый запрос, обычным уровнем. **Замер** главного файла: gzip — 565 КБ, zstd — 531 КБ, brotli максимального уровня — **384 КБ** (−32 %). Brotli в Caddy из коробки нет.

**Как лучше:** при сборке класть рядом файлы `.br` и `.gz` (плагин сжатия для Vite) и включить у `@fastify/static` `preCompressed: true`; Caddy уже сжатое не трогает.
**Что это даст:** ещё −30 % трафика на JS и CSS и меньше работы процессору сервера. После Н1–Н2 выигрыш в килобайтах скромнее (примерно 230 → 160 КБ), поэтому приоритет средний.
**Объём работы:** малый. **Риск:** низкий (проверить заголовок `Content-Encoding` и что SSE не задет).

#### Н5. Стили: один файл 248 КБ, блокирует первую отрисовку
**Где:** `apps/web/src/styles/index.css:1-13` (13 файлов склеиваются в один), сборка `dist/assets/index-BafG59Pv.css`.

**Что не так (замер):** 248 КБ / 46 КБ gzip, 2 619 блоков правил, 2 992 селектора, из них 2 294 разных — около 700 переопределений одного и того же в «слоях» (`components.css` → `theme.css` → `theme-player.css`). Стили администратора (`admin.css` + `theme-admin.css`) — около 62 КБ без комментариев, игроку не нужны. По грубой проверке (имя класса не встречается в коде) мёртвых правил немного — около 16 КБ (62 класса: `summary-tiles`, `menu-tiles`, `role-select`, `mark-banner`, `push-prompt` и др.; часть может собираться в коде по кускам — **оценка**).

**Как лучше:** когда страницы администратора станут ленивыми (Н2), подключать `admin.css` и `theme-admin.css` из `GamePage` — Vite сам вынесет их в отдельный файл. Мёртвые классы удалить после проверки поиском. Переписывать слои не нужно.
**Что это даст:** −25 % стилей у игрока (−11 КБ gzip), чуть быстрее первая отрисовка. Польза небольшая.
**Объём работы:** малый. **Риск:** низкий–средний (порядок подключения стилей влияет на вид — сверить снимками).

### Б. Старт: от значка до карты

#### Н6. Три круга запросов подряд и три экрана загрузки; между запусками ничего не помнится
**Где:** `apps/web/src/lib/auth.tsx:41` (`/api/auth/me`), `apps/web/src/main.tsx:33-38` (пока нет ответа — текст «Загрузка…»), `apps/web/src/pages/GamesPage.tsx:66-85` (`/api/games` + `/api/me/teams`, заготовка главной, потом переход на карту), `apps/web/src/pages/TeamPage.tsx:170-177, 366-368, 564-571` («Загружаем карту…»), `apps/web/src/lib/api.ts:23-29` (память `READY` живёт только пока открыта вкладка).

**Что не так:** типичный игрок (одна команда, своих игр нет) при каждом холодном запуске проходит:
1. `/api/auth/me` → экран «Загрузка…»;
2. только после ответа — `/api/games` и `/api/me/teams` → заготовка «Мои команды»;
3. только после ответа — `/api/games/:id/teams` и `/api/games/:id/my-map` → «Загружаем карту…»;
4. карта, затем досыпаются награды, испытания, команды, проходы, мир (ещё 5 запросов), потом служение, рейтинг, летопись (ещё 3).

Три круга строго друг за другом: на мобильной связи это 3 × (0,2–0,5 с) чистого ожидания до того, как карта вообще начнёт строиться (**оценка**), и три сменяющих друг друга экрана загрузки — то самое «подгружается».

**Как лучше (три шага, каждый полезен отдельно):**
1. **Запросы первого круга — сразу и вместе**, до запуска React: `/api/auth/me`, `/api/games`, `/api/me/teams` уходят одновременно (если на устройстве есть отметка «здесь входили»). 3 круга → 2.
2. **Помнить последнюю открытую игру** (`localStorage`: id игры и «команда/администратор») и сразу, тем же первым кругом, запрашивать её `/teams` и `/my-map` и открывать её адрес. 2 круга → 1.
3. **Помнить последний ответ карты и состава между запусками** (IndexedDB или `localStorage`, ключ — пользователь + игра; очищать там же, где `clearReady()`). Код уже умеет «показать прежнее сразу, свежее подменит следом» (`ready()` в `TeamPage.tsx:170-173`) — нужно лишь, чтобы прежнее переживало закрытие приложения.

**Что это даст:** после шага 3 карта прошлого запуска рисуется с первого кадра, свежая приходит через один круг и тихо подменяет. Экраны «Загрузка…» и заготовка главной при обычном входе не показываются вовсе.
**Объём работы:** шаг 1 — малый; шаг 2 — малый; шаг 3 — средний.
**Риск:** низкий для 1–2. Для 3 — средний: секунду видно вчерашнее состояние (так уже работает внутри сеанса); обязательно чистить при выходе и смене аккаунта, не показывать, если игра завершилась.

#### Н7. Одинаковые запросы уходят по два-четыре раза: память не знает про «уже в пути»
**Где:** `apps/web/src/lib/api.ts:24-27` (`apiReady` всегда шлёт запрос; `prefetch` проверяет только готовые ответы), `GamesPage.tsx:76-78, 85`, `TeamPage.tsx:366-368`, `apps/web/src/components/UserAvatar.tsx:8-16, 32, 39`, `apps/web/src/components/AvatarLightbox.tsx:43`.

**Что не так:**
- Главная запускает `prefetch` состава и карты и **в том же кадре** переводит игрока на карту (`GamesPage.tsx:85`). Страница команды смотрит в память — там ещё пусто (ответ в пути) — и шлёт те же два запроса сама. Самый тяжёлый ответ (`my-map`, по образцу — 440 КБ / 49 КБ gzip, см. Н10) у типичного игрока при каждом запуске качается и разбирается **дважды** (**видно из кода**).
- Аватарка участника: `warm()` вызывается на `pointerenter`, `pointerdown` и `focus`, при касании пальцем срабатывают все три, плюс открывшаяся карточка шлёт свой запрос — до **четырёх** одинаковых запросов на одно касание.
- У администратора счётчики (`GamePage.tsx:106-126`) и `prefetch` (`GamePage.tsx:92-93`) качают одни и те же списки параллельно (см. Н17).

**Как лучше:** одна правка в `api.ts`:
```ts
const INFLIGHT = new Map<string, Promise<unknown>>();
export function apiReady<T>(url: string, opts?: { fresh?: boolean }): Promise<T> {
  const cur = INFLIGHT.get(url);
  if (cur && !opts?.fresh) return cur as Promise<T>;
  const p = api<T>(url).then((r) => { READY.set(url, r); return r; }).finally(() => { if (INFLIGHT.get(url) === p) INFLIGHT.delete(url); });
  INFLIGHT.set(url, p);
  return p;
}
```
После своего действия (сдал, взял) звать с `fresh: true`, чтобы не получить ответ, начатый до действия.

**Что это даст:** −2 тяжёлых запроса на каждом запуске, −2–3 на каждом касании аватарки, у администратора −7–8 при входе на страницу игры (**видно из кода**).
**Объём работы:** малый. **Риск:** низкий (следить за `fresh` после действий).

### В. Обновления данных в реальном времени

#### Н10. Карта команды перечитывается целиком слишком часто — и каждый раз вся пересчитывается
**Где:** `apps/web/src/pages/TeamPage.tsx:367` (`loadMap` → `setMap(m)` без сравнения), `:410-415` (таймер 60 с и `focus`), `:369, 184` + `apps/web/src/lib/daytime.ts:193-204` (таймер шторма: `Math.min(wait, 60_000)`, строка 201), `:386-395` (разница по SSE: `structuredClone` всей карты), `:402` (перечитывание по событиям); всего `loadMap()` вызывается в **19 местах** файла. Зависимости расчётов карты: `apps/web/src/pages/TeamMap.tsx:152-171, 227, 256, 270, 277, 319, 397, 441`.

**Что не так:**
- Карта (`my-map` — самый тяжёлый ответ) запрашивается каждые 60 с всегда, даже если вкладка скрыта, и даже когда SSE исправно присылает разницы.
- Если в игре задано расписание шторма, работает **второй** минутный таймер: `useStorm` ждёт «до границы шторма, но не дольше 60 с» и вызывает перечитывание; каждый ответ меняет `map.now`, и таймер заводится снова. Итого до двух полных перечитываний в минуту (**видно из кода**; сколько именно — зависит от задержки сети).
- Каждый ответ — новый объект карты. Почти все расчёты в `TeamMap` завязаны на `map.tasks`, `map.revealed`, `map.edges`, `map.cities` — при новой ссылке всё считается заново: морские маршруты (поиск пути, `TeamMap.tsx:249-256`), модель нажатий, сцена WebGL, слои SVG. То же при каждой разнице по SSE (`structuredClone` даёт новые ссылки на всё). То есть **раз в минуту карта полностью пересобирается, хотя ничего не изменилось** — вероятная причина периодических подвисаний (**видно из кода**; длительность — нужен замер, раздел 6).

**Как лучше:**
1. Сохранять прежние ссылки на неизменившиеся части:
```ts
function keepSame<T extends Record<string, unknown>>(prev: T | null, next: T): T {
  if (!prev) return next;
  const out: Record<string, unknown> = { ...next };
  for (const k of Object.keys(next)) if (JSON.stringify(prev[k]) === JSON.stringify(next[k])) out[k] = prev[k];
  return out as T;
}
// loadMap: setMap((prev) => keepSame(prev, m));  — и то же после applyPatch
```
Сравнение строк — миллисекунды; пересчёт маршрутов и сцены — в разы дороже.
2. Один таймер шторма — ровно на границу (`changesAt`), без минутного опроса до неё.
3. Минутный опрос заменить «сторожем» соединения (Н14): пока SSE живо, опрашивать незачем; при скрытой вкладке не опрашивать.

**Сколько это весит.** Образец ответа `my-map` снят соседним экспертом с локальной копии тестовой партии (файл `map.json` в этой же папке, **замер по образцу**): **440 КБ, по сети ≈ 49 КБ gzip**; 282 дела, 153 открытых перекрёстка. Значит, минутный опрос — это 60–120 ответов в час, то есть **≈ 3–6 МБ мобильного трафика в час на игрока** и разбор 440 КБ JSON с полной пересборкой карты каждую минуту. Попутно: 374 КБ из 440 — список дел, и в каждом деле повторяется полное описание (40 разных дел на 282 записи: 174 КБ вместо 24 КБ). Если описания отдавать один раз справочником, ответ ужимается до 291 КБ / 33 КБ gzip (−34 %) — это уже к отчёту по серверу.

**Что это даст:** карта перестаёт пересобираться вхолостую; трафик на `my-map` падает в разы (с ≈ 3–6 МБ в час до долей мегабайта).
**Объём работы:** шаг 1 — малый; шаги 2–3 — малый–средний.
**Риск:** низкий для 1 (поведение то же, ссылок меньше меняется); для 3 — средний, делать только вместе со сторожем.

#### Н11. Своё действие = отправка + полное перечитывание карты + ещё одно через 3 секунды
**Где:** `apps/web/src/pages/TeamPage.tsx:439-444` (`act`: `await api(POST)` → `await loadMap()`), то же в `:446-453, 456-464, 476-485, 493, 516, 523`; `:386-388` (разница с «чужой» базой → `mapLater()`); сервер `apps/api/src/services/teamMap.ts:586-607`.

**Что не так:** после «Взять дело» кнопка ждёт два круга: отправку и полный `my-map`. Затем сервер через 300 мс присылает по SSE разницу «от версии N к N+1», а у игрока уже N+1 (только что скачал) — проверка `cur.rev !== m.base` считает это расхождением и ставит **ещё одно** полное перечитывание через 2,5–4 с. Итог каждого своего действия: POST + 2 × `my-map` + две полные пересборки карты.

**Как лучше:**
- В `onMapPush` первой строкой: `if (cur && m.kind === "patch" && m.rev === cur.rev) return;` — эта версия уже есть.
- Дальше (по желанию): не ждать `loadMap()` в `act` — разница всё равно придёт по SSE через 0,3 с; или пусть сервер в ответе на действие сразу отдаёт новую карту.

**Что это даст:** −1 тяжёлый запрос и −1 пересборка карты на каждое действие (первая строка); отклик кнопки на один круг быстрее (второй шаг).
**Объём работы:** первая строка — малый (минуты); второй шаг — средний.
**Риск:** первая строка — низкий; второй шаг — средний (нужна страховка, если SSE отвалилось).

#### Н12. Номер версии карты растёт, даже когда карта не менялась, — разницы наполовину не срабатывают (на стыке с сервером)
**Где:** `apps/api/src/services/teamMap.ts:577` (`MAP_TTL_MS = 60_000`), `:617-619` (`rev: ++mapRev` при каждом пересчёте), клиент `TeamPage.tsx:388`.

**Что не так:** готовая карта на сервере живёт 60 с; первый же опрос после этого пересчитывает её и выдаёт **новый номер версии**, хотя содержимое то же. Игроки одной команды опрашивают в разные секунды, поэтому в любой момент часть держит версию N, часть N+1. Когда приходит настоящее изменение, разница считается от N+1 — все, кто ещё на N, вместо лёгкой разницы делают полное перечитывание. Механизм разниц (решение 24.10) из-за минутного опроса работает примерно у половины клиентов (**видно из кода**; долю покажет замер).

**Как лучше:** на сервере при пересчёте сравнить новую карту с прежней и, если равны, оставить прежний номер. Тогда клиент при опросе видит тот же `rev` и может вообще не трогать состояние. Подробности — в отчёте по серверу.
**Что это даст:** разницы срабатывают у всех; минутный опрос, пока он есть, перестаёт вызывать пересборку.
**Объём работы:** малый. **Риск:** низкий.

#### Н13. Каскад: каждое обновление состава команды тянет ещё четыре запроса
**Где:** `apps/web/src/pages/TeamPage.tsx:379` (`useEffect(…, [team, loadBattles, …])`), `:366` (`setTeam` — каждый раз новый объект), `:334-347` (`loadBattles` зависит от `team`), `:399` (событие `tasks` → перечитать состав).

**Что не так:** эффект, который грузит испытания, положение команд, проходы и мир, зависит от объекта `team`. Каждый ответ `/teams` — новый объект, значит эффект срабатывает заново. А состав перечитывается при каждом событии о делах своей команды. Получается: **любое дело в команде (взяли, сдали, одобрили) → у каждого, кто в сети: `/teams` + `my-battles` + `standings` + `my-passages` + `peace`** — 5 запросов вместо одного, плюс то, что событие вызывает и так. При входе с главной (когда состав уже в памяти) эти четыре запроса уходят дважды.

**Как лучше:** зависеть от `team?.id`, а в `loadBattles` брать id команды из `ref`:

```ts
useEffect(() => { if (team?.id) { void loadBattles(); void loadStandings(); void loadPassages(); void loadPeace(); } }, [team?.id]);
```
**Что это даст:** −4 запроса на каждое событие о делах у каждого игрока команды; −4 при входе.
**Объём работы:** малый. **Риск:** низкий (обновление этих четырёх и так идёт по своим событиям, `TeamPage.tsx:403-406`).

#### Н14. Возврат в приложение: данные обновляются через 5–7 секунд, карта грузится дважды
**Где:** `apps/api/src/routes/events.ts:26` (`retry: 3000`), `:28` (пульс — строка-комментарий `: ping`), `apps/web/src/lib/useGameEvents.ts:17-27, 34-44`, `apps/web/src/pages/TeamPage.tsx:396-409, 410-415`.

**Что не так:**
- Телефон в фоне рвёт SSE. По возвращении браузер переподключается через 3 с (`retry`), потом событие «перечитай всё» ждёт склейку 2,5–4 с. Испытания, команды, внимание обновляются через **5,5–7 с** после возврата (**видно из кода**).
- Карта при этом может загрузиться дважды: сразу по `focus` и ещё раз после переподключения. Причём слушается только `focus`, а не `visibilitychange`; на телефоне `focus` при возврате в приложение приходит не всегда (**нужен замер** на iPhone и Android).
- «Молчащее» соединение (мобильная сеть оборвала связь без уведомления) браузер не замечает: пульс сервера — комментарий, до кода он не доходит. Страховкой служит минутный опрос карты (Н10).

**Как лучше:** один обработчик «вернулись»: `visibilitychange → visible` после паузы больше ~20 с — сразу пересоздать `EventSource` и один раз, без задержки склейки, перечитать состав, карту и остальное (с защитой от дублей из Н7). Пульс сервера сделать именованным событием (`event: ping`) и на клиенте пересоздавать соединение, если 60–70 с тишины, — тогда минутный опрос карты можно убрать.
**Что это даст:** после разблокировки телефона всё свежее через один круг (0,3–0,5 с) вместо 5–7 с; −1 лишняя загрузка карты; основание убрать опрос.
**Объём работы:** средний. **Риск:** средний (проверить на плохой связи; сторож не должен переподключаться слишком рьяно).

#### Н15. Несколько соединений SSE одновременно

#### Н16. Таймер «раз в секунду» перерисовывает всю страницу команды и всю карточку города

#### Н17. Администратор: счётчики качают 9 полных списков на каждое событие; «Проверка» опрашивает 6 блоков каждые 15 секунд; главная качает карты всех игр

#### Н18. Нет защиты от устаревших ответов

### Д. Шрифты

#### Н22. Шрифты перепроверяются по сети при каждом запуске — текст «перещёлкивается»; два файла лежат дважды
**Где:** `apps/api/src/app.ts:119-123` (для всего, что не `assets/` и не картинки, — `Cache-Control: no-cache`, сюда попадают `/fonts/*.woff2`), `apps/web/vite.config.ts:18-24` (шрифтов нет ни в предзагрузке, ни в правилах кэша SW), `apps/web/src/styles/base.css:3-12` (`font-display: swap`), `apps/web/index.html` (нет `preload` шрифтов), `apps/web/public/fonts/`.

**Что не так:**
- Заголовок `no-cache` значит «перед каждым использованием спроси сервер, не изменилось ли». Шрифты игры (Philosopher и Literata, кириллица и латиница — около 10 файлов, 412 КБ) при каждом холодном запуске ждут 10 запросов-проверок. Пока ответа нет, `font-display: swap` рисует текст запасным шрифтом (Georgia), потом заменяет — заголовки и кнопки «прыгают». Чем хуже связь, тем заметнее. Без сети приложение останется без своих шрифтов вовсе.
- **Замер:** `literata-400-cyrillic.woff2` и `literata-600-cyrillic.woff2` — один и тот же файл (одинаковая контрольная сумма), так же `literata-400-latin` и `literata-600-latin`. Браузер качает их по разным адресам дважды: лишние 134 КБ.

**Как лучше:**
- Сервер: для `/fonts/` — `public, max-age=31536000, immutable` (при замене шрифта менять имя файла).
- SW: добавить `fonts/*.woff2` в `globPatterns` (или правило `CacheFirst` для `/fonts/`).
- `index.html`: `<link rel="preload" as="font" type="font/woff2" crossorigin href="/fonts/philosopher-700-cyrillic.woff2">` и ещё два-три главных файла.
- Literata: одно описание с `font-weight: 400 600` на один файл (если шрифт вариативный) или убрать дубль.

**Что это даст:** со второго запуска шрифты берутся с телефона мгновенно — текст не мигает; −10 запросов на старте; −134 КБ при первом заходе (**замер**).
**Объём работы:** малый. **Риск:** низкий (проверить полужирное начертание Literata после объединения).

#### Н23. Шрифт Inter с Google Fonts блокирует первую отрисовку
**Где:** `apps/web/index.html:19-21`, `apps/web/src/styles/tokens.css:63-64` (Inter — только поля ввода и запасной для интерфейса).

**Что не так:** строка `<link rel="stylesheet" href="https://fonts.googleapis.com/…">` в `<head>` — браузер не рисует страницу, пока не получит этот файл с чужого сервера. При первом заходе (кэша SW ещё нет) это лишние соединения с двумя серверами Google; если Google отвечает медленно или недоступен в сети игрока, первая отрисовка ждёт. **Как лучше:** положить Inter рядом с остальными шрифтами (один вариативный файл на кириллицу, один на латиницу) или заменить на системный шрифт (`system-ui` уже стоит в запасных) — решение за владельцем, вид полей ввода может чуть измениться. Строки `preconnect` и правило SW для Google тогда убрать.
**Что это даст:** первый заход не зависит от стороннего сервера; −2 соединения.
**Объём работы:** малый. **Риск:** низкий (сверить вид полей ввода).

### Ж. Сервис-воркер и выдача сервером

#### Н27. Новая версия перезагружает страницу посреди игры

**Объём работы:** малый. **Риск:** низкий–средний (вкладка, открытая сутки без касаний, обновится по правилу «нет касаний»).

## 5. Что сделано хорошо — не трогать

- **Память готовых ответов** `ready / apiReady / prefetch` (`lib/api.ts:18-29`) — правильный приём «показать прежнее сразу, свежее подменит». Его нужно не менять, а распространить (Н19–Н21) и дополнить защитой от дублей (Н7).
- **Карта команды разницами по SSE** (`useGameEvents.ts`, `TeamPage.tsx:386-395`, сервер `teamMap.ts`) и **склейка перечитываний со случайной добавкой** (`useCoalesced`) — грамотно; мешают только соседние механизмы (Н10–Н12).
- **Заготовка геометрии карты в простое** (`mapWarm.ts`) и память тяжёлой геометрии (`lib/keep.ts`).
- **Кэш статики**: файлы сборки с хэшем — «навсегда», картинки — на месяц; в SW отдельный кэш аватарок, чтобы не вытесняли картинки карты; у островов в адресе хэш содержимого.
- **Оболочка из кэша SW** (`navigateFallback`): приложение стартует без сети до первого запроса данных.
- **Картинки**: всё в webp, аватарки и гербы в двух размерах, `loading="lazy"` у аватарок, ролик «Об игре» — `preload="metadata"` с обложкой (14 МБ не качаются, пока не нажали).
- **Графики вынесены** в отдельный файл и подключают только нужные части ECharts; серверный код из общего пакета (`mapgen`) в сборку сайта не попал — отсев неиспользуемого работает.
- **Свои шрифты с разбивкой** на кириллицу и латиницу (`unicode-range`).
- **Собственные замеры**: `lib/perf.ts` шлёт время первой отрисовки и плавность карты с реальных устройств, `?perf=1` показывает их на экране. По ним и стоит сверять «до / после».
- **Часы испытания** (`components/TrialClock.tsx`) — образец: тикает маленький компонент и только пока идёт время.
- **Сжатие и протокол**: Caddy сжимает ответы и держит HTTP/2 и HTTP/3 — много мелких запросов идут по одному соединению.

Замер: стенд, инструменты разработчика → «Сеть», столбцы «Размер» и «Время» при входе на карту, с ограничением скорости «Fast 3G / Slow 4G». От этого зависит точный выигрыш Н6 в секундах.

3. **Время разбора 1,9 МБ программы на телефоне (Н1, Н2).** Замер: «Производительность», холодный запуск на среднем Android и на iPhone; строка «Evaluate script» у `index-….js`. Ожидание — десятки–сотни миллисекунд (оценка).
4. **Мигание шрифтов (Н22).** Замер: запись экрана холодного запуска установленного приложения на мобильной связи; во вкладке «Сеть» — 10 ответов 304 на `/fonts/`.
