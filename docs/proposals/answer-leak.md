# Защита ответов от «своей игры» — варианты на согласование

Статус: предложение (13.09). Ничего не реализовано.

## Где дыра

- Создать игру может любой вошедший пользователь (`POST /api/games`), он сразу становится её администратором.
- Администратору город отдаётся целиком: районы, задания **с ответами**, знак шифра, прогресс команд (`GET /api/games/:id/cities/:nodeKey`, панель города на карте администратора).
- Значит, игрок регистрирует второй аккаунт (почта не обязательна), создаёт «свою» игру, генерирует карту и читает ответы всех 66 городов. Задания одни и те же во всех играх (содержимое платформы).

Что при этом **не** утекает: шифры конвертов и ключи — свои в каждой игре; дела — свои у каждой церкви; ход чужой игры не виден.

## Варианты

### A. Закрыть создание игр

**1. Игры создают только организаторы, которых подтверждает суперадмин.**
Новый пользователь вместо «Новая игра» видит форму «Хочу провести игру в своей церкви» (название церкви, город, короткий текст). Суперадмин в дашборде подтверждает — у пользователя появляется право организатора, его церковь заведена. Дальше он создаёт игры и добавляет соадминистраторов сам, но только из числа тех, кто **не играет** ни в одной идущей игре (см. 3).
- За: закрывает дыру полностью, это же давно отложенный пункт про организации и лимиты для суперадмина.
- Против: у вас появляется очередь на подтверждение (уведомление на почту, одна кнопка). Первые пользователи-организаторы уже есть — им право выдаётся сразу миграцией.
- Стоимость: средняя (роль организатора, заявка, экран у суперадмина, письмо).

**2. Код приглашения организатора.**
Суперадмин выдаёт одноразовые коды; создать игру можно только с кодом. Проще заявки, но код можно передать дальше.
- За: почти нулевая стоимость.
- Против: код утекает так же, как пароль; контроля меньше, чем в 1.

### B. Не показывать ответы там, где они не нужны

**3. Играющий не может быть администратором.**
Пользователь, состоящий в команде идущей игры, не может создать игру и не может быть добавлен администратором, пока игра не завершена (и наоборот: администратора нельзя пригласить в команду его игры). Второй аккаунт это обходит, поэтому вариант только в паре с 1 или 2.
- За: дёшево, снимает соблазн «одним кликом».
- Против: сам по себе не защищает.

**4. Ответы скрыты от администратора по умолчанию.**
Панель города показывает задания без ответов. Ответ виден только там, где он нужен для решения: в карточке спора по конкретному заданию и в блоке «Проверка». Полный список ответов — только суперадмину. Если организатору нужен полный список (готовить встречу, проверять вручную), суперадмин включает ему флаг «видит ответы» на игру.
- За: даже при утечке аккаунта администратора или при сговоре ответы не открыты одним списком; администратору для ведения игры ответы почти не нужны.
- Против: организаторы иногда хотят видеть всё; решается флагом.
- Стоимость: небольшая (фильтр в одном маршруте, флаг игры, две правки интерфейса).

**5. Тестовые действия («Отдать город», «Зачесть задания») только в черновике и в тестовых играх.**
Сейчас они позволяют администратору мгновенно открыть любой город в идущей игре. Оставить их для игр с пометкой «тестовая» (ставит суперадмин) и для черновика.
- За: убирает быстрый путь к содержимому «через игру».
- Против: вам самим они нужны для проверок — для этого и пометка «тестовая».

### C. Видеть, если кто-то всё же пытается

**6. Журнал просмотров ответов.**
Каждый запрос полного города администратором пишется в журнал (кто, какая игра, какой город, когда — только идентификаторы). Суперадмин видит в дашборде «игры с одной командой, где просмотрено N городов за час», и список свежих игр с их создателями.
- За: ловит и то, чего мы не предусмотрели; дёшево.
- Против: это обнаружение, а не запрет.

**7. Ответы не отдаются клиенту вовсе.**
Проверка ответа уже идёт на сервере; можно отдавать администратору ответ только по отдельному запросу с записью в журнал (6) и с задержкой показа (например, ответ показывается на 30 секунд). Мешает массовому копированию, не мешает точечной проверке.
- За: усиливает 4 и 6.
- Против: неудобство при честной проверке.

### D. Сделать чужие ответы бесполезными

**8. Вариативность заданий между играми.**
При генерации игры для каждого города выбирается подмножество и порядок заданий, у заданий с выбором перемешиваются варианты, у «числовых» — часть заданий с параметрами (глава, имя) подставляется случайно. Чужая игра тогда показывает не те задания.
- За: снижает ценность любой утечки, включая скриншоты.
- Против: контента для настоящей вариативности мало (871 задание на 66 книг), параметризация — большая работа по содержанию. Не как основная мера.

## Что рекомендую

Набор **1 + 3 + 4 + 5 + 6**:

| Мера | Что даёт |
|---|---|
| 1. Организатор по подтверждению суперадмина | закрывает вход |
| 3. Играющий ≠ администратор | убирает «одним кликом» |
| 4. Ответы скрыты по умолчанию, видны в споре и по флагу | уменьшает ущерб от любой утечки |
| 5. Тестовые действия только в черновике и тестовых играх | закрывает обход «через игру» |
| 6. Журнал просмотров в дашборде | видно попытки |

Вариант 2 (коды) — если не хотите подтверждать заявки руками. Вариант 8 — отдельно и позже, как работа с содержанием.

Что потребуется: роль организатора и заявка (модель, два маршрута, экран у суперадмина, письмо), флаг игры «тестовая» и «видит ответы», фильтр ответов в маршруте города и в панели, проверка членства при создании игры и добавлении администратора, журнал просмотров (таблица без содержимого) и блок в дашборде. Тесты на каждую проверку доступа.

Вопросы владельцу:
- Подтверждаете набор? Нужен ли вариант 2 вместо заявок?
- Кто из существующих пользователей должен сразу получить право организатора (по никнеймам, вы назовёте сами)?
- Нужен ли организаторам полный список ответов по умолчанию или только по флагу?
