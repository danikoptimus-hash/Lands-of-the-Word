# Развёртывание

## Первичная настройка сервера (один раз)

На сервере от root:

```
curl -fsSL https://raw.githubusercontent.com/danikoptimus-hash/Lands-of-the-Word/main/deploy/bootstrap.sh -o bootstrap.sh
bash bootstrap.sh landsoftheword.com
```

Скрипт идемпотентный: повторный запуск безопасен. Что он делает — в шапке `bootstrap.sh`.

## Ветки и тестовый стенд

- `staging` → тестовый стенд `test.<домен>` (workflow `deploy-test`, скрипт `deploy/deploy-test.sh`, стек `deploy/docker-compose.test.yml`, проект `lotw-test`, каталог `~/lotw-test` пользователя deploy, переменные `deploy/.env.test` создаются сами). Почта и вход через Google на стенде выключены.
- `main` → продакшен (workflow `deploy`, `deploy/deploy.sh`); перед миграциями делается дамп в `/opt/lotw-backups`.
- Копия боевой базы на стенд: workflow `copy-db-to-test` (Run workflow) или `bash ~/lotw-test/deploy/copy-db-to-test.sh` на сервере.
- DNS: для стенда нужна A-запись `test` на тот же адрес сервера; сертификат Caddy получит сам.
- Логи стенда: `docker logs --tail 100 lotw-app-test`.

## Что делает и чего не делает выкладка (с 15.11)

- **Одна выкладка за раз.** Прод и стенд живут на одном сервере; скрипты `deploy.sh` и `deploy-test.sh` берут общий замок
  (`flock` на каталоге `/opt/lotw`): вторая выкладка ждёт первую, а не падает на скачивании образа («lease does not exist»).
- **Обновляется только приложение.** Скрипты скачивают только образ приложения. База (`postgres:16-alpine`) и прокси
  (`lotw-caddy`) сами при выкладке больше не обновляются — раньше свежий образ мог перезапустить базу или прокси посреди дня.
  Обновить их осознанно, ночью: `cd /opt/lotw/deploy && docker compose pull db caddy && docker compose up -d`
  (база перезапустится на несколько секунд, прокси разорвёт соединения прода и стенда).
- **Ошибка миграции на проде останавливает выкладку.** Новая версия не запускается, прежняя продолжает работать, запуск
  в GitHub Actions краснеет. Раньше новая версия стартовала на старой структуре базы. На стенде контейнеры к этому
  моменту уже убраны, поэтому стенд поднимается в любом случае, а запуск краснеет в конце.
- **Пока приложение перезапускается, прокси придерживает запросы** до 20 секунд (`lb_try_duration` в `caddy/Caddyfile`),
  а не отвечает ошибкой 502.
- **Настройки прокси** берутся из каталога прода и применяются выкладкой прода. Caddyfile смонтирован в контейнер одним
  файлом, а git при обновлении заменяет файл — контейнер продолжал бы видеть прежний. Поэтому `deploy.sh` сравнивает файл
  в контейнере с файлом в репозитории и, если они разные, сначала проверяет новый (`caddy validate`), затем
  перезапускает прокси (остановка не дольше трёх секунд, затем проверка, что прокси работает и видит новый файл;
  несколько секунд без связи у прода и стенда). Непрошедший проверку файл не применяется.
  Проверить, какой файл видит прокси: `docker exec lotw-caddy grep -c lb_try_duration /etc/caddy/Caddyfile`.
- **Один экземпляр приложения.** Подписчики событий, готовые ответы, номера версий карт и таймеры живут в памяти процесса
  (`services/events.ts`, `views.ts`, `teamMap.ts`): второй экземпляр «для скорости» запускать нельзя — события одного
  не дойдут до игроков другого, а таймеры сработают дважды.
- **Журнал приложения ограничен** (5 файлов по 20 МБ). У базы и прокси ограничения пока нет: его добавление пересоздаёт
  контейнер, это делается вместе с осознанным обновлением.

## Нагрузочный прогон стенда

Workflow `loadtest` (кнопка Run workflow; решение владельца 23.10). Параметры: число участников, команд, секунд нагрузки и разгона, решений администратора и сдач дел в минуту. Что происходит: по SSH в контейнере стенда `node apps/api/dist/scripts/loadtest.js seed` создаёт учётки `test_lt_*`, их сессии и запущенную партию «Нагрузочный тест»; файл сессий забирается на машину Actions по scp (в журнал не попадает); `scripts/loadtest.mjs` ведёт себя как страницы команд (карта и соседние ответы, поток событий, перечитывание по событиям, сдачи дел, решения администратора); параллельно по SSH снимается `docker stats` стенда и прода; в конце `loadtest.js clean` всё удаляет. Итог — таблица задержек по запросам и нагрузка сервера в сводке запуска. Сервер один на прод и стенд, поэтому запускать ночью по поясу игры.

## Выгрузка данных партии для исследования

Через игру выгрузок нет (решение владельца 02.10). Данные одной партии снимаются скриптом на сервере от root:

```
bash /opt/lotw/deploy/research-export.sh "Осень"
```

Скрипт пишет CSV по таблицам (команды, участники с никами, летопись, события заданий, состояния городов, паузы, дела,
испытания, разведка, карта) и собирает архив `/root/lotw-research-<дата>.tgz`. В выгрузку не попадают пароли, почта,
сессии, ссылки сброса и подтверждения, push-подписки. Архив забирается на компьютер командой `scp`, которую скрипт печатает в конце.

## Ограничение запросов (Caddy)

Caddy собран со сторонним модулем `rate_limit` (`deploy/caddy/Dockerfile`, образ `ghcr.io/danikoptimus-hash/lotw-caddy`, собирается тем же workflow, что и приложение). Сверх лимита — ответ 429.

Пороги — решение владельца 22.09: вход и регистрация — 30 запросов в минуту, остальное — 300 за 10 секунд. С этапа 2 ревизии скорости (решение владельца 16.11: «только `/api` и по игроку») считается так:

| Зона | Что считается | Чей счёт | Порог |
|---|---|---|---|
| `auth` | вход, регистрация, сброс пароля (`/api/auth/*`, кроме «кто я», «аккаунты на устройстве», «способы входа») | адрес сети | 30 в минуту |
| `player` | запросы игры (`/api/*`) с cookie сессии | игрок (cookie сессии) | 300 за 10 секунд |
| `guest` | запросы игры без cookie сессии | адрес сети | 300 за 10 секунд |
| `address` | все запросы игры | адрес сети | 3000 за 10 секунд |

Картинки, шрифты и файлы программы не считаются. Зона `address` — потолок на адрес: без него подставной cookie позволял бы обойти ограничение с одного адреса; число (вдесятеро выше лимита игрока) выбрано при правке и может быть изменено владельцем.

Отказы пишет сам модуль в журнал прокси: `docker logs lotw-caddy 2>&1 | grep -i "rate limit"` (по описанию модуля; на сервере не проверялось).

Настройки проверяет конвейер выкладки (шаг «Проверка настроек прокси» в `deploy-test.yml` и `deploy.yml`): тот же образ Caddy с модулем запускает `caddy validate`. Вручную: `DOMAIN=example.org caddy validate --config deploy/caddy/Caddyfile --adapter caddyfile` (нужен caddy с модулем: `https://caddyserver.com/api/download?os=linux&arch=amd64&p=github.com/mholt/caddy-ratelimit`). На стенд ограничение не действует: у `test.<домен>` его нет.

## Автодеплой (GitHub Actions)

Каждый push в рабочую ветку (кроме правок только в `docs/`, `assets/raw/`, `*.md`) запускает `.github/workflows/deploy.yml`:
1. собирает Docker-образ приложения и публикует в GitHub Container Registry `ghcr.io/danikoptimus-hash/lotw-app` (шаг пропускается, пока в репозитории нет `Dockerfile`);
2. по SSH заходит на сервер пользователем `deploy` и запускает `deploy/deploy.sh`: обновляет код, скачивает образ, перезапускает контейнеры, применяет миграции.

Нужные секреты репозитория (Settings → Secrets and variables → Actions → New repository secret):

| Секрет | Значение |
|---|---|
| `DEPLOY_HOST` | IP сервера |
| `DEPLOY_USER` | `deploy` |
| `DEPLOY_SSH_KEY` | приватный ключ, специально созданный для деплоя (см. ниже) |

Создание ключа деплоя — на сервере от root:

```
ssh-keygen -t ed25519 -N "" -C "github-deploy" -f /root/deploykey
cat /root/deploykey.pub >> /home/deploy/.ssh/authorized_keys
cat /root/deploykey
```

Вывод последней команды (от `-----BEGIN OPENSSH PRIVATE KEY-----` до `-----END OPENSSH PRIVATE KEY-----` включительно) вставить в секрет `DEPLOY_SSH_KEY`, после чего удалить файлы: `rm /root/deploykey /root/deploykey.pub`.

Запуск вручную: вкладка Actions → deploy → Run workflow.

## Почта (восстановление пароля, уведомления)

Письма уходят через SMTP. Пока в `deploy/.env` нет `SMTP_HOST`, письма не отправляются, и восстановить пароль нельзя.

### Вариант без оплаты и без настройки DNS: почтовый ящик Gmail

1. Завести отдельный ящик Gmail для сайта (например, `landsoftheword@gmail.com`), включить в нём двухэтапную проверку.
2. В настройках Google-аккаунта → «Безопасность» → «Пароли приложений» создать пароль приложения (16 символов).
3. На сервере дописать в `deploy/.env`:

```
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USER=landsoftheword@gmail.com
SMTP_PASS=пароль приложения
MAIL_FROM=Земли Слова <landsoftheword@gmail.com>
```

4. Перезапустить: `cd /opt/lotw/deploy && docker compose up -d app`.
5. Проверить: в настройках аккаунта суперадмина есть кнопка «Проверить почту» — она показывает ошибку подключения словами и шлёт тестовое письмо.

Порт **587**, а не 465: у Hetzner для новых аккаунтов исходящие порты 25 и 465 закрыты (открывают по запросу в поддержку после первого оплаченного счёта), 587 открыт.

Лимит Gmail — около 500 писем в сутки, для восстановления паролей и уведомлений хватает. Так же работают Яндекс (`smtp.yandex.ru`, 465) и Mail.ru (`smtp.mail.ru`, 465) с паролем приложения.

### Вариант «как положено»: сервис рассылок со своим доменом

Resend (бесплатно до 3 000 писем в месяц) или Mailgun: добавить домен `landsoftheword.com`, внести в DNS Porkbun записи SPF/DKIM, которые покажет сервис, взять SMTP-логин и ключ и вписать их в `deploy/.env` так же, как выше (`SMTP_HOST=smtp.resend.com`, `SMTP_PORT=465`, `SMTP_USER=resend`, `SMTP_PASS=API-ключ`, `MAIL_FROM=Земли Слова <noreply@landsoftheword.com>`).

Ключи и пароли только в `deploy/.env` на сервере, в репозиторий их не класть.

## Вход через Google

Кнопка «Войти через Google» появляется на странице входа, только когда в `deploy/.env` заданы **оба** значения: `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET`. Без них вход по никнейму и паролю работает как раньше, а `GET /api/auth/google` отвечает 404. Из Google сайт берёт только почту и идентификатор учётки (scope `openid email`): имя и фото не запрашиваются и не хранятся.

1. [Google Cloud Console](https://console.cloud.google.com/) → создать проект (или взять существующий) → «APIs & Services» → «OAuth consent screen»: тип External, название «Земли Слова», почта поддержки; scopes — только `openid` и `email`; опубликовать (Publishing status: In production), иначе входить смогут только тестовые пользователи.
2. «Credentials» → «Create credentials» → «OAuth client ID» → тип «Web application»:
   - Authorized JavaScript origins: `https://landsoftheword.com`
   - Authorized redirect URIs: `https://landsoftheword.com/api/auth/google/callback` (ровно так: адрес собирается из `PUBLIC_URL` + `/api/auth/google/callback`).
3. Скопировать Client ID и Client secret и дописать на сервере в `deploy/.env`:

```
GOOGLE_CLIENT_ID=….apps.googleusercontent.com
GOOGLE_CLIENT_SECRET=…
```

4. Перезапустить: `cd /opt/lotw/deploy && docker compose up -d app`. Переменные попадают в контейнер через `deploy/docker-compose.yml` (секция `environment` сервиса `app`), как и SMTP.

Секрет — только в `deploy/.env` на сервере; в репозиторий и в GitHub Secrets его класть не нужно (деплой не передаёт переменные приложения, он только обновляет код и образ). Для локальной разработки те же переменные можно положить в `apps/api/.env` с redirect URI `http://localhost:3000/api/auth/google/callback`.

## Настройки базы и стенд на одном сервере

- **Настройки базы** задаёт `deploy/db-settings.sh` при каждой выкладке (прод и стенд): память под кэш файлов и сортировки, цена
  чтения «вразброс» для SSD, сжатие журнала изменений, журнал медленных запросов (дольше 300 мс, без значений параметров —
  в них бывают тексты игроков). Применяются без перезапуска базы и хранятся в её томе. Посмотреть медленные запросы:
  `docker logs lotw-db 2>&1 | grep duration`. Вернуть настройки «из коробки»:
  `docker exec lotw-db psql -U lotw -d lotw -c "ALTER SYSTEM RESET ALL" -c "SELECT pg_reload_conf()"`.
- **Стенд не отнимает процессор у игры**: в `docker-compose.test.yml` у контейнеров стенда вес процессора 256 против обычных
  1024 — при нехватке игре достаётся вчетверо больше, без нехватки стенд работает в полную силу; память стенда ограничена
  (приложение 512 МБ, база 384 МБ).

## Бэкапы и восстановление

Дамп базы делается каждый день в 22:30 по часам сервера (UTC) — это 03:30 по Ташкенту, когда игра спит; с низким приоритетом (`deploy/backup.sh`, cron пользователя deploy) в `/opt/lotw-backups`, хранятся 14 последних. Проверить, что бэкапы идут:

```
ls -la /opt/lotw-backups
```

Восстановить из дампа (на сервере от root):

```
bash /opt/lotw/deploy/restore.sh /opt/lotw-backups/lotw-ГГГГ-ММ-ДД-ЧЧММ.sql.gz
```

Скрипт останавливает приложение, пересоздаёт базу, заливает дамп и запускает приложение. Рекомендуется раз в месяц проверять восстановление на копии: `docker compose exec -T db pg_restore` не нужен — дампы в формате plain SQL.
