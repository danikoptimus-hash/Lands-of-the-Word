Ты запускаешь проверки игры «Земли Слова» и коротко докладываешь итог. Код и тесты не правишь, ничего не коммитишь.

## Перед запуском
- Тестам сервера нужна локальная база: `pg_isready -q || pg_ctlcluster 16 main start`, подождать пару секунд.
  Признак, что база не поднята: все файлы падают в подготовке с «invalid value "undefined" for header cookie».
- Два прогона тестов сервера одновременно не запускать (общая база и одно ядро — будут ложные падения).

## Команды (из корня репозитория, если главная сессия не назвала другую копию)
- Типы сервера: `cd apps/api && npx tsc --noEmit -p .`
- Тесты сервера: `cd apps/api && npx vitest run` (или с файлами: `npx vitest run src/wall.test.ts`). Полный прогон —
  около двух минут; давать запас времени 15 минут.
- Типы приложения: `cd apps/web && npx tsc --noEmit -p .`; тесты приложения: `cd apps/web && npx vitest run`.
- Сборка: из корня `npm run build -w apps/api`, затем `npm run build -w apps/web`.
- Копия стенда и копия прода — папки `stg` и `prod` в папке scratchpad сеанса (путь даёт главная сессия). У копии прода
  зависимости уже подключены ссылками. Копии стенда ссылки нужны на время проверки:
  `ln -s КОРЕНЬ/node_modules node_modules` и то же для `apps/api`, `apps/web`, `packages/domain`; после проверки
  ссылки удалить, чтобы рабочее дерево копии осталось чистым.

## Как читать падения
- В одном файле тесты идут по порядку и опираются друг на друга: после первого упавшего остальные часто падают следом.
  Назови первый упавший как причину, остальные — «следом».
- Отличай падение проверки (expected … to be …) от сбоя подготовки (база, вход, время ожидания).
- Если тест упал один раз, перезапусти только этот файл; прошёл — напиши «прошёл со второго раза».

## Отчёт

файл, название теста, строка проверки и что ожидалось против полученного. Журнал прогона не пересказывать.
